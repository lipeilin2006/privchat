# 安全与信任模型

本文记录 PrivChat 的威胁模型、信任边界、已知问题与密码学参数。
基于 `main` 分支（SimpleX 式单向队列协议）。

---

## 1. 信任边界

| 角色 | 谁负责它的可信度 | 客户端对它的假设 |
|---|---|---|
| **mailbox 节点**（存储转发） | **用户自己**：用哪台、是否自建，由用户决定 | 只提供传输与存储；**内容安全完全不依赖它** |
| 洋葱中继（可选） | 用户配置 | 只做逐层转发，看不到明文 |
| 对端设备 | 对端自己 | 只信任「拿到邀请的人」 |
| 本机 | 用户自己 | SQLCipher + 密码 |

结论：**mailbox 可以是恶意的**。它能破坏可用性、能看元数据，
但看不到也用不了消息内容——内容安全由端到端密钥保证，不依赖节点诚实。

---

## 2. 协议概要

```
邀请   = (mailbox, queue_id, owner_ek, sender_sk)   // 线下交换（二维码/链接）
建立   = 双方各自建一条接收队列；互扫后 root = HKDF(DH(ek_a, ek_b))
消息   = ChaCha20-Poly1305(AAD = header(n, ek, nonce))
队列   = Ed25519 签名 (domain || queue_id || 密文)，节点验签后存储
读取   = owner 签名 (domain || queue_id)，节点取回即删
```

- 每条连接独立密钥，**没有全局身份**：换设备/重装 = 重新加好友。
- 方向链按公钥字典序区分，双方不会用同一条链。
- 链密钥每条消息推进一次（对称棘轮），乱序窗口 200。

---

## 3. 恶意 mailbox 能做什么

| 能力 | 影响 | 客户端是否可检测 |
|---|---|---|
| 读取/丢弃/延迟消息 | 可用性 | 不能（但不会丢密钥） |
| 留存密文（harvest now, decrypt later） | 与设备失窃叠加时才有意义 | 不能 |
| 重放旧消息 | 无（序号 + 已用密钥拒绝） | 能，直接丢弃 |
| 存垃圾 / 绕过验签 | 无（收端解不开） | 能（解密失败） |
| 统计时间、大小、队列对 | 元数据泄漏 | 不能 |
| 删除队列 | 可用性 | 不能 |

**它不能**：解密、伪造可解密的消息、把 A 的消息冒充成 B 的。
签名只绑定「写权限」，真正的身份由邀请携带的连接公钥决定。

## 4. 已知问题（按严重度）

| # | 问题 | 说明 |
|---|---|---|
| S1 | ~~没有前向保密对抗设备失窃~~ | ✅ 已修复：派生完两条链立刻丢弃 `root`，状态里只留当前链位置；拿到数据库只能影响未读消息。 |
| S2 | ~~无后妥协恢复~~ | ✅ 已修复：每 100 条消息由连接公钥较小的一方发起换钥（epoch+1），对方收到后用同一 epoch 换掉**自己的**密钥、随下一条消息头下发——两边都换，单侧设备被短期拿走也换不出后续密钥。旧 epoch 保留宽限状态，切换瞬间在路上的消息仍可解。 |
| S3 | 元数据 | 已做明文桶填充（同桶密文等长）+ 每 500 条消息轮换入站队列（可换到另一台 mailbox，旧队列排空后删除）；时间与「同一连接的两条队列」仍可关联。 |
| S4 | 可用性 | 每条队列绑定一台 mailbox；节点故障期间消息不可达（靠 TTL 兜底）。队列轮换时可切到另一台。 |
| S5 | 队列写权限即邀请 | 邀请泄露 = 可以往队列灌垃圾（但解不开）。现阶段没有轮换写 key 的 op。 |
| S6 | ~~节点侧无速率限制~~ | ✅ 已修复：单队列限额（默认 1000 条 / 64 MiB）+ 队列总数上限（默认 5 万）+ 建队列令牌桶（20/s，突发 60）+ 并发连接上限（信箱 64 / 中继 128）+ 单请求读取上限 2MB；TTL 到期清理。 |
| S7 | 洋葱为可选 | 开启后队列请求会逐层包好、经中继转发到 mailbox，中继只看到「上一层」和「下一跳」；首跳仍能看到上传者的 TLS 身份（每条连接独立身份，已缓解）。单包内层上限 60KB（线上是 JSON 数组，实际约 4KB 以内的文本），很长的单条消息会被拒绝。 |

## 4.5 节点接口保护

| 接口 | 谁可调用 | 保护手段 |
|---|---|---|
| `queue_create` | 任何人（先到先得） | 令牌桶 20/s（突发 60）；队列总数上限 5 万 |
| `queue_send` | 持 invite 里 sender 私钥的人 | Ed25519 验签，签名绑定 queue_id；单队列条数/字节上限 |
| `queue_get` / `queue_delete` | 持 owner 私钥的人 | Ed25519 验签；取回即删 |
| 洋葱中继（relay） | 任何人 | 并发上限 128；单包 128KB；可选中继白名单；单跳超时 90s |
| 洋葱终点（mailbox） | 任何人 | 与信箱共用并发上限 64；单包 128KB；只收终点层，转发一律拒绝 |
| 全部接口 | — | 单请求读取上限 2MB；systemd 沙箱（只读根、无 capability、私有 tmp） |

已知边界（不打算用密码学解决，靠运营手段）：

- `queue_create` 没有身份，只能限速 + 限量；慢速刷满 5 万条（约 40 分钟）
  仍可能挤掉新用户，需要运营侧监控/清理。
- `queue_send` 的密文可以重放：E2E 会拒绝，但会占掉队列配额。
- 队列满时 `queue_get` 响应可达 64MB，而客户端读取上限 16MB、中继 32MB——
  大积压走洋葱会失败，建议洋葱路径配合较短的轮询周期。
- 中继默认不限下一跳（空名单=放行），公开部署建议在 config.json 里配
  `onion_peers`，否则可能被当成开放转发节点。

## 5. 密码学参数

| 项 | 取值 |
|---|---|
| 连接密钥交换 | X25519，`root = HKDF(SHA-256, DH)` |
| 链推进 | HKDF-SHA256，每条消息一次；每 100 条换一次整条链（epoch+1），双方各自轮换自己的连接密钥 |
| 消息加密 | ChaCha20-Poly1305，头部作 AAD |
| 队列签名 | Ed25519，覆盖 `domain || queue_id || payload` |
| 乱序窗口 | 200 条（每个 epoch 独立） |
| 本地库 | SQLCipher（全库加密） |
| 邀请编码 | base64url，约 150 字符 |

## 6. 形式化验证

`/root/privchat-proverif/privchat_conn.pv`（ProVerif 2.05）验证：

- 载荷保密：恶意 mailbox + 邀请泄露（拿到写权限）仍解不开；
- 认证：接收方接受的消息必由发送方发出；
- 前向保密（链密钥层面）：拿到推进后的链密钥解不开旧消息。

**未覆盖**：设备失窃（S1）——已通过「不保留 root」在实现层处理，模型未建模状态泄露。
反证对照 `privchat_conn_neg.pv` 说明模型非空。

## 7. 部署建议

- mailbox 自建或选可信运营者（信任边界在用户）。
- 单条队列仍然绑一台信箱（S4 单点）；多备一台作为轮换目标，坏一台还能换过去。
- 生产环境开启洋葱时，中继与终点分离运营。
- TTL 按需调短，减少元数据留存。
